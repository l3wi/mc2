---
title: Secrets & volumes
description: Cluster secret injection (name/env/allowHosts), volume mounts, the top-level volumes declaration, and name resolution.
---

Secrets carry encrypted values into a guest; volumes carry durable node-local
directories.

## `secrets[]`

| Key | Required | Default | Description |
| --- | --- | --- | --- |
| `name` | yes | — | Cluster secret name (`mc2 secret set <name>`). |
| `env` | yes | — | Guest env var receiving the value (placeholder until injected). |
| `allowHosts` | no | `[]` | Hosts the real value is attached to. Empty → the desired set fails closed. |

```yaml
services:
  web:
    image: alpine:3.20
    secrets:
      - name: SMOKE_TOKEN
        env: API_TOKEN
        allowHosts: [api.example.com]
```

Secrets come from the cluster's secret store (`mc2 secret set <name>`) rather
than from the stack file — the file only names them. With an empty
`allowHosts`, the desired set **fails closed**: the value is never injected.

### Precedence: `environment` overrides secrets

An explicit `environment:` entry **overrides** `secrets[].env` with the same
name — the colliding secret is dropped (not decrypted) and the env value wins.
A warning is logged per service on collision.

<Callout type="warning" title="Collision is not an error">
  If `environment: { API_TOKEN: plain }` and a secret also injects
  `API_TOKEN`, the secret is silently dropped and the plain env value wins.
  A warning is logged per service — check apply output if a secret seems
  missing.
</Callout>

`environment:` is direct injection; `secrets[].env` is encrypted and
host-gated. See [Secrets](/documentation/concepts/secrets).

## `volumes[]` (mounts)

| Key | Required | Description |
| --- | --- | --- |
| `name` | yes | A declared top-level `volumes` key. |
| `target` | yes | Absolute guest path; unique per service. |

```yaml
services:
  db:
    image: postgres:16
    volumes:
      - name: data
        target: /var/lib/postgresql/data
```

Mounted as node-local named directory volumes; data survives sandbox recreate
and is retained on removal. See
[Storage](/documentation/concepts/storage) and the
persistent-volumes example.

## `volumes` (top-level)

| Key | Required | Default | Description |
| --- | --- | --- | --- |
| `kind` | no | `dir` | Only `dir` (named directory volume) in v1. Disk images, quotas, and snapshots are not yet supported. |

```yaml
volumes:
  data:
    kind: dir
```

Service mounts must reference a declared top-level `volumes` key; undeclared
mounts are rejected at apply.

## Volume naming & resolution

Volume names must match `[a-z0-9][a-z0-9._-]*` and must not contain `--`.
Resolved per-stack to `mc2-<stack>--<volume>` at sandbox create time; stored
under the server's named-volume root (`mc2 server --volume-dir`, default
`~/.microsandbox/volumes`).

<Callout type="tip" title="Why `--` is banned in stack names">
  `--` is the volume namespace separator — `mc2-<stack>--<volume>` would be
  ambiguous if a stack or volume name itself contained `--`, so both are
  rejected.
</Callout>
