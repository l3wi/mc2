Secrets carry encrypted values from the cluster store into a guest; volumes
carry durable host directories into a guest. Neither value lives in the stack
file — the file only names them.

## `secrets[]`

| Key | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `name` | string | yes | — | Cluster secret name, as used by `mc2 secret set <name>`. |
| `env` | string | yes | — | Guest environment variable that receives the value. Must be non-empty. |
| `allowHosts` | list of strings | no | `[]` | Hosts the real value may be attached to. Must list at least one host, or the instance fails. |

```yaml
services:
  web:
    image: alpine:3.20
    secrets:
      - name: SMOKE_TOKEN        # set with `mc2 secret set SMOKE_TOKEN`
        env: API_TOKEN
        allowHosts: [api.example.com]
```

How injection works:

- The value is stored encrypted at rest (XChaCha20-Poly1305, with the secret
  name as associated data) and is set out of band:
  `mc2 secret set NAME --value …`, `MC2_SECRET_VALUE`, or stdin.
- The guest sees a **placeholder** in `env`; MC2 substitutes the real value
  only on TLS connections to one of `allowHosts`. An empty `allowHosts` is a
  hard error for that instance (`allowHosts must list at least one host`), so
  the value can never be attached everywhere.
- A missing secret name, or an empty `allowHosts`, fails only that instance
  (`Failed`) — the rest of the stack keeps running.
- An explicit `environment:` entry with the same variable name **overrides**
  `secrets[].env`: the secret is dropped (never decrypted) and a warning is
  logged per service on collision.

```text
 stack.yaml                MC2 store (encrypted)         guest VM
┌──────────────────┐      ┌────────────────────┐      ┌────────────────────┐
│ secrets:         │      │ mc2 secret         │      │ API_TOKEN=         │
│  - name: TOKEN ──┼─────►│   TOKEN = <value>  │─────►│  <placeholder>     │
│    env: API_TOKEN│      │ allowHosts gated   │      │                    │
│    allowHosts:   │      └────────────────────┘      │ real value only on │
│      [api.ex.com]│                                  │ TLS to api.ex.com  │
└──────────────────┘                                  └────────────────────┘
```

See [Secrets](/documentation/concepts/secrets) for the threat model.

## `volumes[]` (mounts)

| Key | Type | Required | Description |
| --- | --- | --- | --- |
| `name` | string | yes | A key declared under the top-level `volumes`; undeclared names are rejected. |
| `target` | string | yes | Absolute guest path; must be unique within the service. |

```yaml
volumes:
  data:
    size: 10GiB
services:
  db:
    image: postgres:16
    command: ["postgres"]
    volumes:
      - name: data
        target: /var/lib/postgresql/data
```

One volume may be mounted by several services and by several replicas of one
service — they share the same host directory. Write only `name` and `target`
on a mount; a host path is never accepted. (Normalized specs, as returned by
the API, also carry `sizeMib`, filled from the volume's `size` — it isn't a
per-mount override.)

## `volumes` (top-level)

| Key | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `kind` | string | no | `dir` | Only `dir` (a named host directory) in v1; disk images and snapshots are not supported. |
| `size` | size | no | `10GiB` | Quota for the directory. Compose byte sizes (`10GiB`, `512m`, or bytes); must be positive and ≤ 1 TiB. |

```yaml
volumes:
  data:
    kind: dir
    size: 20GiB
```

## Volume size semantics

A volume is an MC2-owned host directory bind-mounted into the guest. `size` is
an enforced **write quota**. It doesn't preallocate disk, but it does count
toward the server's disk budget: with `--limit-disk-mib`, apply reserves each
volume's `size` once (plus `storage_opt.size` per replica) and rejects a
stack that doesn't fit.

```text
 host                                          guest
 <data-dir>/volumes/mc2-shop--data (or --volume-dir)
        │  bind mount, quota = size − current usage
        ▼
 /var/lib/postgresql/data   df shows the declared size; writing past it
                            fails with ENOSPC (No space left on device)
```

- The quota is recomputed each start as `size − <current usage>`, so a
  half-full volume can still use the full declared size.
- **Resize** by changing `size` and re-applying: the data is kept, the VM
  restarts, and the new quota applies. Shrinking below the directory's current
  usage is rejected at apply with the current usage in the message.
- **Retention:** `mc2 down` keeps volumes; `mc2 down --volumes` deletes them.
  `mc2 volume ls` lists what is retained on the node.
- The root is resolved as `--volume-dir` (env `MC2_VOLUME_DIR`) or
  `<data-dir>/volumes`, i.e. `~/.mc2/volumes` with the default data dir. A
  volume directory is named `mc2-<stack>--<volume>`.
- Guests also have a writable root disk (`storage_opt.size`, default 4 GiB);
  when either that or a volume fills, MC2 reports the condition in `mc2 ps`
  and from `mc2 exec`/`mc2 ssh open`/`mc2 logs`. See
  [Services](/references/stack/services#cpus-mem_limit-storage_opt).

## Naming

Volume names must match `[a-z0-9][a-z0-9._-]*`, must not contain `--` or end
with `-`, and are at most 63 characters.

<Callout type="tip" title="Why `--` is banned in stack names">
  `--` is the volume namespace separator — `mc2-<stack>--<volume>` would be
  ambiguous if a stack or volume name itself contained `--`, so both are
  rejected. (`.` is allowed in volume names only, never in stack/service/network
  names.)
</Callout>

See [Storage](/documentation/concepts/storage) for how volumes relate to the
guest's root disk and what survives a recreate.
