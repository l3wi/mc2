---
title: Secrets
description: Server-wide encrypted-at-rest secrets with host-gated injection, versus plaintext environment.
---

MC2 gives services two distinct ways to get values into the guest environment.
They look similar in YAML and both end up as env vars, but they are different
mechanisms with very different security properties. `environment:` is direct,
plaintext injection. `secrets[].env` is a reference to an encrypted,
host-gated value. This page explains the difference and when to use which.

## `environment:` — direct injection

```yaml
services:
  web:
    image: alpine:3.20
    environment:
      MODE: fast
      DEBUG: "0"
```

- Plain literal env vars, written inline in the stack file.
- Stored **unencrypted** in the stack spec and injected into the sandbox
  unconditionally at create.
- Visible to every command in the guest. Anyone who can read the stack file or
  the data dir sees the values.
- A change to any value triggers a sandbox recreate.
- Keys starting with `MSB_` are rejected by the microsandbox SDK (reserved
  prefix).

**Use for**: non-sensitive configuration — ports, flags, feature toggles.

## `secrets[].env` — host-gated, encrypted

```yaml
services:
  web:
    image: alpine:3.20
    secrets:
      - name: SMOKE_TOKEN
        env: API_TOKEN
        allowHosts:
          - api.example.com
```

The value is **not** stored in the stack and is **not** injected like an env
var. The stack only references a server-wide secret by name.

- The value lives once in the **server-wide secret store** (`mc2 secret set
  NAME --value …`), encrypted at rest. MC2 never echoes it back: `mc2 secret
  ls` and the REST API return names and metadata only.
- At reconcile time the node decrypts it server-side, just-in-time, and passes
  it to the sandbox through the microsandbox **secret** mechanism — not as a
  plain env var.
- The guest **does not get the raw value**. It sees a generated placeholder
  (`$MSB_<env>`).
- The sandbox's egress proxy enables **TLS interception**. When the guest
  connects to an `allowHosts` host, the proxy injects the real value for that
  connection. Anywhere else the placeholder stays.
- `allowHosts` must be non-empty — injection **fails closed** otherwise.

<Callout type="warning" title="allowHosts must be non-empty">
  If `allowHosts` is empty, the secret is never attached — the sandbox fails
  closed rather than receiving the value on every connection.
</Callout>

**Use for**: credentials and tokens that must be encrypted at rest, never
listed, and scoped to specific outbound hosts.

## Scope: server-wide, not per-stack

Compose secrets are scoped to one compose project. MC2 secrets are a
**server-wide (cluster-wide) store**: there is no stack-level declaration and
no stack namespace. A secret set once is referenceable by name from any stack
on the server. See [Add secrets](/documentation/guides/add-secrets) for the
workflow.

## Precedence on collision

If `environment:` and `secrets[].env` name the **same** env var, the explicit
`environment:` value **wins**. The colliding secret is dropped at desired-set
build — never decrypted, no placeholder, no TLS-interception side effect — and
MC2 logs a warning naming the overridden var.

```yaml
environment:
  API_TOKEN: inline-value        # wins — secrets[] entry for API_TOKEN is dropped
secrets:
  - name: VAULT_TOKEN
    env: API_TOKEN
    allowHosts: [api.example.com]
```

<Callout type="note">
  Because `environment:` wins, a plaintext entry silently neutralizes a
  colliding secret. Check the warning log after apply if you rely on a secret
  that shares a name with an env var.
</Callout>

## Rotation

Rotating a secret is a two-step operation:

1. Re-set the value: `mc2 secret set NAME --value '<new-value>'`.
2. Re-apply the stack so the sandbox is recreated and the new value is
   attached.

The old value is not pushed to running sandboxes in place; a recreate is what
carries the new value into the guest.

## Comparison: `environment:` vs secrets

| | `environment:` | `secrets[].env` |
| --- | --- | --- |
| Declared | inline in the stack file | referenced by name; value not in the stack |
| Stored | plaintext in the stack spec | server-wide store, encrypted at rest |
| Injected | unconditionally at create | host-gated, placeholder + TLS interception |
| Visible to guest | always | only on connections to `allowHosts` |
| Listed by `mc2 secret ls` | n/a | names and metadata only |
| Best for | non-sensitive config | credentials and tokens |

See the [Secrets & volumes reference](/references/stack/secrets-volumes) for
the exact stack schema.
