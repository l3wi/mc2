description: The API token — how it's created, stored, checked, rotated, and when it's switched off.

Authentication protects the control plane. `mc2 server`'s REST API drives
everything — applying stacks, setting secrets, exec into microVMs — so
whoever can call it controls your installation. MC2 guards it with one
bearer token.

## The token

The server creates one API token (`mc2at_…`) the first time it initializes
a data dir. Every `/v1` request must carry it, **including from loopback**;
only `GET /health` is public.

```text
 first start ──► token generated ──► shown once (terminal)
                       │             or <data-dir>/bootstrap-token (0600)
                       ▼
               mc2.db keeps a SHA-256 hash only

 request ──► Authorization: Bearer mc2at_… ──► hash matches? ──► handled
                                                         └───► 401
```

- **Shown once.** In a terminal it's printed to stderr. Without one
  (systemd, containers) it's written to `<data-dir>/bootstrap-token` with
  mode 0600 and only the path is logged — the value never reaches your log
  collector. Read the file, save the token, delete the file.
- **Stored as a hash.** The database holds only a SHA-256 hash; reading
  `mc2.db` doesn't give anyone a usable token.
- **Full authority.** A token holder can apply and remove stacks, set and
  delete secrets, attach secrets to workloads, and exec into any microVM.
  The API never returns stored secret values, but control of workloads is
  control of what they can reach. Treat the token like a root password.

## Rotating it

Lost or leaked? On the server machine:

```bash
mc2 server token rotate --data-dir ~/.mc2
```

It prints a new token once, and the old one stops working immediately —
whether or not the server is running, because every request is checked
against the database. Update your contexts:

```bash
mc2 context set prod --api https://mc2.example.com --token 'mc2at_<new>'
```

Don't restore an old data dir to "recover" a token; rotate.

## `--no-auth`

`mc2 server --no-auth` skips the token check for **that run only**. The token
still exists; the next normal start requires it again.

| Server start | Result |
| --- | --- |
| `--no-auth` on a loopback `--bind` | allowed (lab use) |
| `--no-auth --bind 0.0.0.0:7443` | refused |
| ...plus `--allow-unauthenticated-remote` | allowed, with a warning on every start |
| `--no-auth` with `--public-hostname` | always refused |

<Danger title="Never --no-auth on anything reachable">
  Without the token, any network path to the server is full control of it
  and of every microVM.
</Danger>

## Transport

The CLI calls a URL **local** if its host is in `127.0.0.0/8`, `::1`, or
`localhost`, and **remote** otherwise. For remote URLs it requires
`https://` and refuses to send the token over plain HTTP unless you pass
`--allow-insecure-http` (or set `MC2_ALLOW_INSECURE_HTTP=1`).

The server doesn't enforce this — it serves plain HTTP on its bind address.
Keep `--bind` on loopback and publish the API through Traefik with
`--public-hostname`, so TLS is terminated before the token crosses a
network.

## Where tokens live on clients

Contexts in `~/.mc2/config.toml` hold tokens in plaintext; the CLI writes the
file with mode 0600. Keep it that way, and treat copies of it as secrets. For
CI, prefer `MC2_API_KEY` from your CI's secret store over a contexts file.

The CLI resolves the URL and token separately (flag, then environment
variable, then context), so `--api` alone still sends the current context's
token. See [Identity & contexts](/documentation/concepts/identity-and-contexts).
