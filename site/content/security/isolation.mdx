title: Isolation
description: What separates a guest from the host and from other guests — the microVM boundary, egress profiles, and storage.
---

Every replica is a microVM with its own kernel, root disk, and network
device. That hardware-virtualized boundary is MC2's core security property.
This page explains what it separates, and the deliberate openings through
it: networks, volumes, and published ports.

## A microVM per replica

Containers run in the host kernel's namespaces; a kernel exploit in one is
one step from the host. MC2 replicas each boot their own kernel inside the
hypervisor.

| | MC2 (microVM) | Container |
| --- | --- | --- |
| Kernel | one per replica | shared host kernel |
| Root filesystem | own disk per replica | layered on the host kernel |
| Network | own device, egress policy per service | host network namespace |
| Escape must cross | the hypervisor | the kernel syscall surface |

<Note>
  The isolation model needs a hypervisor: KVM on Linux, Hypervisor.framework
  on Apple Silicon. `mc2 doctor` checks for it.
</Note>

## Egress profiles

`network.profiles` decides what a guest may reach outbound. It's a closed
set; any other value is rejected at apply.

| Profile | Guest may reach | Notes |
| --- | --- | --- |
| `public` (default) | public internet addresses | also the default for an empty list |
| `private` | private/LAN addresses (RFC 1918, IPv6 ULA, CGN) | **not** "MC2 services only" — it reaches other machines on your LAN |
| `host` | the host's own services through the VM's gateway, including the MC2 API and every published loopback port | refused unless the server runs `--allow-host-profile` |
| `none` | nothing | networking disabled, including service networks; must be the only entry |

Profiles combine: `[public, private]` allows both. On top of the profile,
MC2 adds narrow rules for exactly the service-network ports the guest may
reach, so `public` or `private` never cut it off from its peers.

```yaml
network:
  profiles: [none]      # a list, even for one value
```

<Warning title="host gives a guest the control plane">
  With `host`, a guest can reach `127.0.0.1:7443` and every published port on
  the host. It still needs the token to use the API, but it's a large hole in
  the boundary. Keep `--allow-host-profile` off unless you need it.
</Warning>

## Service networks

Services on the same network can reach each other's exposed ports — by
default, with no allow-list. That's convenient and it's a trust decision:
every service on a network is trusted by every other service on it. Put
services that shouldn't talk on different networks. See
[Networking](/security/networking).

## Host ports

Published and exposed ports bind the host's loopback. Nothing is reachable
from outside the host unless you route it through ingress. Without the
`host` profile, a guest reaches only the specific service-network ports it
was granted — not other loopback listeners.

## Storage

- **Root disks are private.** A guest's writes outside volumes stay on its
  own disk, never touch the image or another guest, and are discarded when
  the microVM is recreated.
- **Volumes are shared by name.** A volume is a directory on the host; every
  service or replica in the stack that mounts it reads and writes the same
  files, whatever networks they're on.

## What a compromised guest can do

It's contained by the microVM: it can't read other guests' root disks or
open host ports. It **can** reach whatever its egress profile allows, every
exposed port on its networks, the contents of any volume it mounts, and —
through allowed hosts — use the secrets it was given. The host and
hypervisor underneath remain trusted, which is why patching them is on the
[hardening checklist](/security/hardening).
