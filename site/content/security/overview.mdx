---
title: Security overview
description: The trust boundary between operator, control plane, host, and guest microVMs — what MC2 guarantees and what you own.
---

MC2 runs one trusted process on one host and boots untrusted workloads as
microVMs. Its security model follows from that shape: a small trusted core
(`mc2 server` and the host under it), an operator who authenticates to that
core, and guests treated as hostile from the moment they boot.

## Who's who

- **Operator** — you, or anything holding the API token. The token grants
  full control of the installation.
- **Control plane** — the `mc2 server` process: REST API, SQLite state,
  encrypted secret store, reconcile loop, network splices, SSH listeners, and
  the Traefik catalog writer. It creates and manages microVMs through the
  embedded microsandbox runtime.
- **Host** — the machine running the server and the hypervisor (KVM on
  Linux, Hypervisor.framework on macOS). Trusted; MC2 doesn't re-verify it.
- **Guests** — the microVMs, each with its own kernel, root disk, and
  network device. **Untrusted**: assume any of them can be compromised.

```text
 operator (mc2 CLI / REST client, holds the token)
    │ remote: HTTPS through Traefik        local: HTTP on loopback
    ▼                                        │
┌── host (trusted) ────────────────────────┼─────────────────────────┐
│                                          ▼                         │
│  Traefik (yours) ──── API ────► mc2 server  127.0.0.1:7443         │
│  TLS, public ports              REST · SQLite · secrets · loop     │
│        │                                │                          │
│        │ published ports                │ microsandbox runtime     │
│        ▼                                ▼                          │
│  ┌── guests (untrusted) ─────────────────────────────────────────┐ │
│  │ microVM A      microVM B      microVM C      ...              │ │
│  │ own kernel · own root disk · own network device               │ │
│  └───────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────┘
```

The boundary that matters most is guest-to-host: a compromised microVM must
not become a compromised host, and must reach only what it was granted.

## What MC2 guarantees

- **A kernel per replica.** Every replica is a microVM, not a container on
  the host kernel. An escape has to cross the hypervisor boundary.
- **Loopback host ports.** Published and exposed ports bind `127.0.0.1`.
  Nothing listens publicly unless your Traefik does.
- **Token-protected API.** Every `/v1` route needs the API token unless the
  server was started with `--no-auth` (refused on non-loopback binds without
  an extra flag, and with `--public-hostname`). Only `/health` is public.
- **Secrets encrypted in MC2's store and never listed back.** Guests see a
  placeholder; the real value is added to HTTP headers of requests to the
  hosts you allow, and requests carrying it anywhere else are blocked.
- **Fail closed.** A microVM whose service-network port has no MC2 listener
  isn't created, an unknown egress profile is rejected, and a sandbox owned
  by another install is never adopted or touched.

## Limits to know

- **The runtime keeps a plaintext copy of secrets** in its own database
  (`~/.microsandbox`) while a microVM exists. Protect it like the secrets key.
- **Allowed hosts can echo secrets back** to the guest; allow only hosts you
  trust with the value.
- **Service networks are default-allow.** Every service on a network can
  reach every exposed port on it. Separate networks separate services.
- **Volumes can be shared.** Every service or replica mounting the same
  volume sees the same files.
- **The CLI enforces HTTPS, the server doesn't.** The server speaks plain
  HTTP on its bind address; keep it on loopback and put TLS in front.

## What you own

- **TLS, ACME, and DNS.** MC2 writes Traefik routes; you run Traefik.
- **The host.** Patch the kernel and hypervisor; restrict who can log in.
- **Images.** MC2 doesn't sign, pin, or scan images. A malicious image is
  code running in your microVMs.

<Callout type="warning" title="You are responsible for">
  - Running `mc2 server` as a dedicated user that owns the data dir.
  - Keeping auth on — `--no-auth` only for a disposable loopback lab.
  - HTTPS for any remote control plane.
  - Backing up `mc2.db` with `secrets.key`, and protecting both.
  - Protecting `~/.mc2/config.toml` on clients (it holds tokens) and the
    runtime's `~/.microsandbox` on the server.
  - Vetting the images you run.
</Callout>
