title: Security overview
description: The trust boundary between control plane, node, and guest — and what MC2 guarantees versus delegates.
---

MC2's security model is best understood as three trust layers. The **control
plane** is the `mc2 server` process — SQLite state, REST API, scheduler, and a
reconcile loop. The **node** is the host machine it runs on. The **guest** is
each replica microVM the server boots. Where those layers meet, and what each
one is trusted to do, defines what MC2 protects and what you must protect
yourself.

## The trust boundary

- **Control plane** — `mc2 server` holds the operator API token, the
  server-wide secret store, contexts, and the SQLite state. It is the only
  process that talks to the sandboxes through the embedded microsandbox SDK.
- **Node** — the host runs the hypervisor (`/dev/kvm` on Linux, Apple Silicon
  HVF on macOS) and the sandbox runtime. In v1 there is a single node, and it
  is the same machine that runs the server.
- **Guest** — each replica is a detached microVM with its own kernel,
  filesystem, and network boundary. Guests never share a kernel with the host
  or with each other.

The boundary you care about most is the guest-to-host one: a compromised
microVM must not become a compromised host, and a compromised host must not
silently hand your secrets to every guest.

## What MC2 guarantees

- **Kernel isolation per replica.** Every replica is a microVM with its own
  kernel — not a container sharing the host kernel. A guest escape would have
  to cross the VMM/hypervisor boundary, not a syscall filter.
- **Host ports bind loopback.** Published host ports are bound to the host
  only; guests and other services cannot open arbitrary host ports, and the
  public path in is a single controlled ingress.
- **Secrets stay secret.** The secret store is encrypted at rest, `mc2 secret
  ls` and the REST API return names and metadata only, and the guest never
  receives a raw secret value — only a placeholder that is filled on
  connections to declared `allowHosts`.
- **A remote control plane requires https + token.** Any non-loopback API
  endpoint is refused over plaintext unless you explicitly opt in.

## What MC2 delegates

- **TLS and ACME.** MC2 writes Traefik file-provider catalogs, but the
  certificate resolver, DNS, and TLS termination are yours to run (`--public-hostname` + a cert resolver publish the control plane through that
  catalog).
- **Host OS trust.** The hypervisor, host kernel, and sandbox runtime are the
  outer security ring. MC2 does not re-verify the platform underneath it.
- **Image provenance.** MC2 pulls and runs images from registries you
  configure; it does not sign, pin, or verify images on your behalf.

<Callout type="warning" title="You are responsible for">
  - Running `mc2 server` as a dedicated user with a private data dir.
  - Keeping auth on — never `--no-auth` outside a disposable lab.
  - Always https + a token for remote control planes.
  - Backing up the data dir (it holds state, the token, and the secret-store
    key material).
  - Restricting who can read `~/.mc2/config.toml` and the data dir.
  - Keeping the host and hypervisor patched, and vetting the images you run.
  - Operating Traefik TLS/ACME and the public DNS path.
</Callout>
