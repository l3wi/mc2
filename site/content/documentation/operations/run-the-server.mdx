`mc2 server` is the whole orchestrator. This page is the day-2 reference for
running it: flags, environment variables, auth bootstrap, and operational
details. First run is [Quickstart](/documentation/quickstart) (`mc2 setup`).
For the mental model, see [Architecture](/documentation/concepts/architecture).

## Start it

```bash
mc2 setup     # first run: collect flags, print the command
mc2 server    # defaults: data dir ~/.mc2, bind 127.0.0.1:7443, auth on
```

Auth is **on by default**: the server creates an API token on first bootstrap
and shows it once (stderr on a TTY, or `<data-dir>/bootstrap-token` at 0600
otherwise). `--no-auth` runs this process without auth — loopback only unless
you pass `--allow-unauthenticated-remote`. Override `--data-dir /srv/mc2` when
a dedicated service user should own state.

## Server flags

Every flag also has an environment variable. Defaults in parentheses.

| Flag | Env | Default | Purpose |
| --- | --- | --- | --- |
| `--bind` | `MC2_BIND` | `127.0.0.1:7443` | REST listener address |
| `--data-dir` | `MC2_DATA_DIR` | `~/.mc2` | SQLite state, token, volumes root |
| `--secrets-key-path` | `MC2_SECRETS_KEY_PATH` | `<data-dir>/secrets.key` | Encryption key for the secret store |
| `--reconcile-interval-secs` | `MC2_RECONCILE_INTERVAL_SECS` | `10` | Reconcile loop interval |
| `--node-name` | `MC2_NODE_NAME` | — | Node display name (identity is persisted) |
| `--label KEY=VALUE` | — | — | Node labels (repeatable) |
| `--ingress-config-dir` | `MC2_INGRESS_CONFIG_DIR` | — | Traefik file-provider catalog output |
| `--public-hostname` | `MC2_PUBLIC_HOSTNAME` | — | Publish the control plane via ingress |
| `--public-tls-cert-resolver` | `MC2_PUBLIC_TLS_CERT_RESOLVER` | `le` | Cert resolver for the control-plane route |
| `--volume-dir` | `MC2_VOLUME_DIR` | `~/.mc2/volumes` | Root for MC2-owned volume directories (bind mounts) |
| `--no-auth` | `MC2_NO_AUTH` | `false` | Skip API auth for this run (lab only) |
| `--allow-unauthenticated-remote` | `MC2_ALLOW_UNAUTHENTICATED_REMOTE` | `false` | Confirm `--no-auth` on a non-loopback bind |
| `--allow-host-profile` | `MC2_ALLOW_HOST_PROFILE` | `false` | Permit `network.profiles: [host]` (whole host loopback) |
| `--max-connections` | `MC2_MAX_CONNECTIONS` | `256` | Concurrent REST connections; extra ones get `503` |
| `--request-timeout-secs` | `MC2_REQUEST_TIMEOUT_SECS` | `60` | Whole-request deadline for ordinary REST routes (`0` disables) |
| `--max-ssh-sessions` | `MC2_MAX_SSH_SESSIONS` | `64` | Concurrent SSH sessions across every instance listener |
| `--max-ssh-sessions-per-listener` | `MC2_MAX_SSH_SESSIONS_PER_LISTENER` | `16` | Concurrent SSH sessions for one instance listener |
| `--limit-cpus` | `MC2_LIMIT_CPUS` | `0` (unlimited) | Cluster CPU budget |
| `--limit-memory-mib` | `MC2_LIMIT_MEMORY_MIB` | `0` (unlimited) | Cluster RAM budget (MiB) |
| `--limit-disk-mib` | `MC2_LIMIT_DISK_MIB` | `0` (unlimited) | Cluster disk reservation (MiB): volume sizes + root disks × replicas |

`--public-hostname` must be an exact lowercase RFC 1123 hostname (no port,
wildcard or trailing dot) and `--public-tls-cert-resolver` must match
`[A-Za-z0-9_-]+`; the server refuses to start otherwise. Stack `ingress`
hosts, paths and identifiers are validated the same way when you apply.

## Auth bootstrap

1. Run `mc2 server` (no `--no-auth`), or start the command `mc2 setup`
   printed.
2. Capture the token it shows once: printed to stderr on a TTY, otherwise
   written to `<data-dir>/bootstrap-token` (mode 0600) with only the path
   logged.
3. On the client, `mc2 setup client` saves a
   [context](/documentation/guides/manage-a-remote-server). Ad-hoc:
   `export MC2_API_KEY='mc2at_…'` (the CLI already targets the loopback
   default).

The token is not shown again. If you lose it, mint a new one in place — the
old one stops working immediately:

```bash
mc2 server token rotate --data-dir ~/.mc2
```

Then update contexts with `mc2 context set <name> --api <url> --token <new>`.

## Listener limits

Both listeners are admission-controlled, because a stalled client must not
pin resources:

- **REST.** `--max-connections` caps concurrent connections; the connection
  past the cap is answered with `503 Service Unavailable` and closed rather
  than queued (the listener is HTTP/1, so this also bounds concurrent
  requests). A client that does not finish sending request headers within
  30 s is disconnected, and ordinary routes have a whole-request deadline of
  `--request-timeout-secs` (`408` on expiry). `POST /v1/instances/{id}/exec`
  (a command can run for minutes) and `GET /v1/instances/{id}/logs` (an
  infinite SSE stream, with a keepalive comment every 15 s) are **exempt**
  from that deadline. The body limit is axum's 2 MiB default everywhere
  except `exec`, which accepts 16 MiB of `stdin`.
- **SSH.** `--max-ssh-sessions` caps concurrent sessions per server and
  `--max-ssh-sessions-per-listener` per instance; connections beyond either
  cap are closed immediately. A client has 30 s to complete the SSH
  handshake. There is **no idle timeout** — quiet `tmux` and agent sessions
  stay open — but accepted sockets carry TCP keepalive so a peer that
  disappeared is detected.

Behind Traefik every client appears as `127.0.0.1`, so these caps are global;
MC2 has no per-IP limits.

## Resource budgets

`--limit-cpus` / `--limit-memory-mib` / `--limit-disk-mib` are operator
budgets (default unlimited). `mc2 up` **refuses** an apply that would exceed
the reserved CPU/RAM budget or the disk limit, or that exceeds the host's
detected capacity — so an unplaceable stack is rejected up front instead of
sitting `Pending`. `mc2 status` and `/v1/status` report host capacity,
configured limits, reserved CPU/RAM from instance specs, and measured disk
usage. A `Failed`/`Stopped` instance keeps reserving its CPU/RAM as long as
its `restart` policy will bring it back (`always` / `on-failure`); only
`restart: no` releases the capacity, so a full node can never accept an apply
it could not run.

## The node

`mc2 server` is both the control plane and the (single) node: it registers the
local node row **before** the REST listener accepts, so an apply never sees an
empty node list. The node's identity is persisted in the store, so
`--node-name` (or a hostname change) only renames it — placements, and the VMs
behind them, stay put. While the process runs the node is `Ready`; there is no
heartbeat grace period and nothing ever unbinds a workload because a pass was
slow.

Every sandbox the server creates is labelled with this install's id
(`mc2.install`, generated once on first boot). On restart the node lists the
sandboxes carrying that label and adopts them: an adopted sandbox whose applied
config does not match the stack's current spec — including one created before
the server recorded a config hash — is removed and recreated, and a labelled
sandbox that no stack wants any more is deleted. Sandboxes without the label
are never touched, and a sandbox is forgotten only once its removal actually
succeeded (a transient failure is retried on the next pass).

## Observability

- **OTLP metrics:** set `MC2_OTLP_ENDPOINT` before boot; the server exports
  `mc2.server.*` / `mc2.node.*`. Sandbox metrics stay on the msb-metrics
  sidecar. See [Observability](/documentation/concepts/observability).
- **Health:** `mc2 status` and `GET /v1/status`. The unauthenticated
  `GET /health` is the readiness probe: it answers `200` only while the node
  loop is live and a reconcile pass completed within
  `3 × --reconcile-interval-secs + 30 s`; once the loop has stopped or gone
  quiet it returns `503` with a reason, so a service manager or load balancer
  can act on an orchestrator that is up but no longer converging.

## Day-2 notes

- **The data dir is the state.** Back it up; don't hand-edit it.
- **Restart-safe.** Reconcile is idempotent; restarting the server adopts the
  sandboxes it already owns (by install label) and converges again without
  operator action.
- **Supervised, bounded shutdown.** The node loop and the REST listener are
  supervised: if either ends or panics the server logs the cause and exits
  non-zero, so a service manager restarts it instead of leaving a half-dead
  process. On `SIGINT`/`SIGTERM` the server stops accepting, cancels the node
  loop and its SSH/splice listeners, drains in-flight REST for up to 5 s, then
  aborts whatever is left — shutdown finishes within 10 s even with a
  `logs --follow` stream open or a runtime call wedged. The metrics exporter is
  non-critical and is restarted with backoff. Running microVMs are **left
  alone**: they are detached, and adoption on restart picks them up.
- **Volumes live under `--volume-dir`** by default inside the data dir; move
  them explicitly if your durable state must live elsewhere.
