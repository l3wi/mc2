MC2 is pre-release (0.x). This page explains how versions, releases, and state
compatibility work so you can upgrade an install without losing state — and how
to recover when a key or a database is restored on its own.

## Versioning & release channels

- **Production releases** are cut on `main` by release-plz: feature work merged
  from `dev` bumps the **minor** version, hotfixes merged directly to `main`
  bump the **patch** version. Each release creates a `vX.Y.Z` git tag and a
  cargo-dist GitHub Release with checksummed binaries.
- **Nightly prereleases** (`vX.Y.Z-dev.<date>`) are cut from `dev`. They are
  ignored by the changelog and are not considered stable.
- `CHANGELOG.md` is regenerated from conventional commits at release time; PRs
  into `dev`/`main` must update it (a CI gate enforces this).

The workspace is a single released binary (`mc2`) plus internal library crates
that share the workspace version and are never published separately. The
binary's CLI and the server's REST surface are the compatibility contract.

<Callout type="warning" title="Pre-release caveat">
  Before 1.0, migrations and storage formats may change between minor versions.
  Read the release notes in `CHANGELOG.md` for every version you cross before
  upgrading a production install.
</Callout>

## Upgrade an install

```text
stop mc2 server (SIGTERM; running VMs are left alone)
        │
        ▼
back up mc2.db + secrets.key  (volumes: quiesce the apps first)
        │
        ▼
replace the binary
        │
        ▼
start mc2 server  ─►  migrations run on DB open
        │
        ▼
adopt owned sandboxes  ─►  reconcile converges every stack
                           (stale VMs are recreated)
```

<Steps>
  <Step title="Stop the server">
    Send `SIGTERM` (or `systemctl stop mc2`). Shutdown is bounded (≤ 10 s) and
    running microVMs are **left alone** — they are detached and get adopted on
    the next start.
  </Step>
  <Step title="Back up the data dir">
    With the server stopped, copy `mc2.db` and `secrets.key` **together**
    (plus the key at `--secrets-key-path`, if you moved it). The microVMs are
    still running and still writing to their volumes, so for a consistent
    volume backup quiesce the applications first (or use their own backup
    tools), and include `--volume-dir` if it's outside the data dir.
  </Step>
  <Step title="Replace the binary">
    Install the new `mc2` (version-pinned archive with SHA-256 verification, or
    the shell installer) over the old one. There is no separate server package
    or migration tool.
  </Step>
  <Step title="Start the server">
    Start it with the same service definition, flags, and environment as
    before — in particular the same `--data-dir`, `--secrets-key-path`,
    `--volume-dir`, and `--ingress-config-dir`. Migrations run when the
    database is opened, then the server adopts its microVMs and reconcile
    converges every stack from the stored desired state.
  </Step>
  <Step title="Verify">
    ```bash
    mc2 doctor      # host + paths sanity check
    mc2 status      # control plane up, counts, resources
    mc2 ps          # instances Running again
    ```
  </Step>
</Steps>

## Migrations run on open

The store is SQLite and its schema is applied by embedded, versioned migrations
(`crates/mc2-store/migrations/`) every time the database is opened — on server
start and in the `mc2 server token rotate` / `secrets purge` subcommands. There
is no separate "migrate" command and no downtime step. If the stored format is
unrecognized or a migration cannot be applied, the server **fails fast** at
startup rather than running against a half-migrated database.

## What happens to running VMs

Stopping the server leaves microVMs running, but not everything keeps
working: while it's down, the REST API, service-network splices (services
can't reach each other by name), and SSH endpoints are unavailable. On start:

- every sandbox carries this install's label (`mc2.install`);
- on startup MC2 **adopts** the sandboxes it owns, and never touches foreign,
  unlabelled ones;
- an adopted VM whose applied config no longer matches the stack spec is
  removed and recreated, and a stale VM is recognised from the persisted config
  hash (migration 009) — so an upgrade that changes create-time config converges
  instead of leaving an out-of-date VM running. A recreate loses files
  outside volumes.

## Migrating an existing install

- **From an older data dir:** just run the new binary against the old
  `--data-dir`. Migrations run on open; nothing else to do.
- **From Docker Compose:** see
  [Migrate from Docker Compose](/recipes/compose-to-mc2).

## Backups & key handling

State lives in SQLite under `--data-dir`; the API token is stored **only as a
hash**, and secret values are encrypted with `secrets.key`.

- **Back up `mc2.db` and `secrets.key` together.** A restored database whose
  secret rows were encrypted with a key that is missing, or no longer matches,
  is **refused at startup** rather than silently re-keyed.
- **Don't restore an old data dir to recover a token.** The plaintext is gone by
  design; mint a new one with `mc2 server token rotate --data-dir <dir>`
  instead.
- **If the key is truly lost,** `mc2 server secrets purge --data-dir <dir>
  --yes` deletes the undecryptable rows; the server then starts (generating a
  fresh key) and you re-set the values with `mc2 secret set <name>`.
- **Volumes** under `--volume-dir` (default `<data-dir>/volumes`) are plain host
  directories and survive upgrades as long as the path is unchanged.

See [Run the server](/documentation/operations/run-the-server) for the full
data-dir layout.

## Rolling back

The binary is a single release artifact, so rollback is: restore the previous
binary, point it at the backed-up data dir, and start. Forward migrations are
**not** automatically reversible — if the new version migrated the schema,
restore from backup rather than "downgrading in place".

## Key behaviors

- Migrations run on every database open; there is no separate step or command.
- `mc2.db` + `secrets.key` are a pair — back up and restore them together.
- Tokens are hashes; rotate rather than restore.
- Running VMs survive a restart and are adopted (or recreated) on start;
  networking and SSH through MC2 pause while it's down.
