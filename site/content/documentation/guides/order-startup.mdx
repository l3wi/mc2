title: Order startup
description: Hold a service back until its database is healthy, with healthcheck and depends_on.

**You will learn:** make a web service wait until a database is actually
ready — not just started — using `healthcheck` and `depends_on`.

**Prerequisites:** [Scale & restart](/documentation/guides/scale-and-restart).

## The stack

Save this as `ordered.yaml`:

```yaml
services:
  db:
    image: postgres:16
    command: ["postgres"]            # MC2 doesn't run the image's CMD by default
    environment:
      POSTGRES_PASSWORD: lab-only
    healthcheck:
      test: ["CMD", "pg_isready", "-q", "-U", "postgres"]
      interval: 2s
      timeout: 3s
      retries: 5
      start_period: 30s
  web:
    image: python:3.12-alpine
    command: ["python", "-m", "http.server", "8000"]
    ports:
      - "18090:8000"
    depends_on:
      db:
        condition: service_healthy
```

`db`'s health check runs `pg_isready` inside its VM. `web` declares that it
needs `db` to be **healthy**, not merely started.

```text
 db:   Scheduled ──► Running ─────────────────► Running + healthy
                                                        │
 web:  Scheduled ──► Pending (waiting for db) ──────────┴──► Running
```

<Steps>

<Step title="Apply and watch the gate">

```bash
mc2 up -f ordered.yaml
mc2 ps --stack ordered -o json     # repeat every few seconds
```

While Postgres initializes, `web` stays `Pending` with the message:

```text
depends_on: waiting for db (service_healthy)
```

</Step>

<Step title="See it release">

Once `pg_isready` passes, `db` is healthy and the next reconcile pass starts
`web`. In testing this took about 15 seconds with the image already
downloaded.

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:18090/
# 200
```

</Step>

<Step title="Clean up">

```bash
mc2 down ordered
```

</Step>

</Steps>

## How the gate behaves

- **List form** — `depends_on: [db]` means `condition: service_started`: wait
  until any `db` replica is `Running`.
- **`service_healthy`** — wait until any running `db` replica passes its
  health check. The dependency must have an enabled `healthcheck`.
- **First start only.** Once `web` has started, a later restart or a
  recreate after a config change isn't held back, and `db` going down doesn't
  stop `web`. Your application still needs to retry its connection.
- **Same stack only.** Dependencies name services in the same file; unknown
  names and cycles are rejected at apply.

## Tuning the health check

| Key | Default | Meaning |
| --- | --- | --- |
| `interval` | `30s` | Time between probes. |
| `timeout` | `30s` | A probe running longer counts as failed (`0` is rejected). |
| `retries` | `3` | Consecutive failures before the replica is unhealthy. |
| `start_period` | `0s` | Failures in this window after boot don't count. |
| `disable` | `false` | Turn the check off. |

An unhealthy replica is recreated if the service has a `restart` policy, and
reported `Failed` otherwise.

<Note title="Exposing the database">
  To let `web` connect to `db`, add `expose: [5432]` to `db` — see
  [Connect services](/documentation/guides/connect-services). Exposed ports
  are unique on the server *and* must be free on the host's loopback, so this
  is rejected if you already run Postgres locally on 5432. Make Postgres
  listen elsewhere (`command: ["postgres", "-p", "15432"]`) and expose that.
</Note>
