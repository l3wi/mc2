---
title: Manage a remote server
description: Run MC2 on a VPS behind Traefik and HTTPS, and drive it from your laptop with a context.
---

**You will learn:** run `mc2 server` on a VPS, publish its API over HTTPS
through Traefik, and manage it from your laptop exactly as you manage a local
server.

**Prerequisites:** [Open SSH](/documentation/guides/open-ssh) (or any earlier
guide), a Linux VPS with KVM, a DNS name for it (here `mc2.example.com`), and
Traefik 3.x installed on the VPS.

```text
 laptop                          VPS
 ──────                          ───
 mc2 CLI ──HTTPS──► Traefik :443 ──► 127.0.0.1:7443 mc2 server ──► microVMs
 (context "prod")   (Let's Encrypt)   (loopback only)
```

The server keeps listening on loopback. Traefik terminates TLS and forwards
to it; MC2 writes that route itself when you pass `--public-hostname`.

<Steps>

<Step title="Plan the server with the wizard (on the VPS)">

```bash
mc2 setup server
```

It asks for the bind address (keep `127.0.0.1:7443`), data dir, public
hostname (`mc2.example.com`), certificate resolver name (`le`), the
ingress directory (`~/.mc2/ingress`), and whether to write a Traefik static
config (yes, with your ACME email). It then prints the `mc2 server …`
command and a checklist. It never starts anything itself.

With a public hostname, authentication always stays on.

</Step>

<Step title="Start MC2 and Traefik (on the VPS)">

Run the printed command. It will look like:

```bash
mc2 server \
  --ingress-config-dir ~/.mc2/ingress \
  --public-hostname mc2.example.com \
  --public-tls-cert-resolver le
```

Save the API token it prints (or read it from `~/.mc2/bootstrap-token` if it
ran without a terminal, then delete the file). Then start Traefik with the
generated config:

```bash
traefik --configFile ~/.mc2/traefik.static.yml
```

That config listens on `:80` and `:443`, gets certificates from Let's
Encrypt through the `le` resolver, and watches `~/.mc2/ingress/traefik`.

</Step>

<Step title="Open the network path">

Point DNS for `mc2.example.com` at the VPS and allow inbound TCP 80 and 443.
Let's Encrypt needs port 80 to issue the certificate. Check from anywhere:

```bash
curl https://mc2.example.com/health
# {"service":"mc2-server","status":"ok"}
```

</Step>

<Step title="Connect from your laptop">

```bash
mc2 setup client
```

Enter a context name (`prod`), the URL (`https://mc2.example.com`), and the
token. The wizard saves the context in `~/.mc2/config.toml` (mode 0600),
makes it current, and can test the connection. By hand, that's:

```bash
mc2 context set prod --api https://mc2.example.com --token 'mc2at_…'
mc2 context use prod
```

</Step>

<Step title="Use it">

```bash
mc2 status
# mc2 0.1.0 — remote: https://mc2.example.com (context: prod)
#   auth: bearer ✓
mc2 up -f stack.yaml
mc2 ps
```

Every command works as it does locally. Switch back with
`mc2 context use local` (or pass `--context local` for one command).

</Step>

</Steps>

<Note title="Published ports stay on the VPS">
  `ports` bind the **server's** loopback. `curl 127.0.0.1:18091` on your
  laptop won't reach them; use an SSH tunnel
  (`ssh -L 18091:127.0.0.1:18091 you@vps`) or give the service an
  [ingress](/documentation/guides/publish-with-ingress) hostname.
</Note>

## Remote means HTTPS

The CLI calls any non-loopback URL **remote** and refuses plain `http://` for
it, because the token would cross the network unencrypted. To override for a
trusted private network, pass `--allow-insecure-http` or set
`MC2_ALLOW_INSECURE_HTTP=1`.

Authentication is separate from that: the server requires the token on
every `/v1` request, local or remote, unless it was started with `--no-auth`
— which is refused with `--public-hostname`.

## Running it as a service

For a real VPS, run `mc2 server` and Traefik under systemd rather than in a
terminal. See [Run the server](/documentation/operations/run-the-server) for
a unit file, supervision, and backups.
