Single-machine path for **Linux (KVM)** and **macOS Apple Silicon (HVF)**.

MC2 is a YAML-driven orchestration system for microsandbox: one process
(`mc2 server`) keeps state in SQLite, serves REST, and drives sandboxes
through the embedded microsandbox SDK — no separate agent, no daemon, no gRPC
seam.

## Prerequisites

| | Linux | macOS |
| - | ----- | ----- |
| CPU | amd64 or arm64 | **Apple Silicon only** |
| Hypervisor | KVM (`/dev/kvm`) | Hypervisor.framework |
| `mc2` | on your PATH | same |

Check host readiness:

```bash
mc2 doctor
```

<Callout type="note" title="Hypervisor is only needed to run sandboxes">
  The REST and scheduler side still serve without a hypervisor; instances just
  fail with a runtime error instead of booting. `mc2 doctor` reports exactly
  what is missing.
</Callout>

## Install

Prebuilt binaries for Linux (amd64/arm64) and macOS (Apple Silicon) ship with
every release:

```bash
curl -fsSL https://github.com/l3wi/mc2/releases/latest/download/mc2-installer.sh | sh
```

Or grab the checksummed `.tar.xz` for your platform from the
[releases page](https://github.com/l3wi/mc2/releases). All commands below
assume `mc2` is on your PATH.

## Run the orchestrator

First run uses the interactive wizard. It needs a TTY; it only scaffolds
config and prints the commands to finish — it never starts the server or
Traefik.

```bash
mc2 setup
```

Jump straight to a tree with `mc2 setup server` (on the host that will run
VMs) or `mc2 setup client` (on your laptop).

1. **Server tree.** Bind address, data dir, API key on/off, optional public
   hostname / Traefik. It prints a copy-paste `mc2 server …` command and a
   finish-setup checklist. Start the server with that command. Auth is on by
   default; the API token prints **once** on first bootstrap — save it.
2. **Client tree.** Context name, control-plane URL, and the token. It saves
   and activates a context in `~/.mc2/config.toml` (0600) and can verify the
   live connection.

Then bring up your first stack:

```bash
mc2 node ls
mc2 up -f examples/01-hello-service/stack.yaml
mc2 ps
curl -s http://127.0.0.1:7443/v1/status | jq .
```

The example runs one HTTP service publishing host port `18091`:

```bash
curl -s http://127.0.0.1:18091/
# hello world
```

<Callout type="note" title="Skip the wizard (lab)">
  Two terminals, no context file, no auth. Defaults are data dir
  `~/.mc2` and bind `127.0.0.1:7443`; the CLI already talks to that
  loopback URL.

  ```bash
  # Terminal 1
  mc2 server --no-auth

  # Terminal 2
  mc2 node ls
  mc2 up -f examples/01-hello-service/stack.yaml
  ```
</Callout>

## What just happened?

Behind that `mc2 up` call:

1. **Published desired state.** The stack YAML was validated (unknown keys are
   rejected, not ignored), the missing `name` was filled from the file name,
   and the normalized document was persisted in SQLite.
2. **Scheduled instances.** The service's `scale: 1` became one instance,
   assigned to the local node, and its declared host port was bound.
3. **Converged.** The reconcile loop built a desired set and drove the sandbox
   through its phase model — `Pending` → `Running`. If it had failed, the
   instance would report `Failed` instead of silently vanishing.
4. **Verified.** `mc2 ps` reads live phase state; `curl` proves the service is
   actually reachable on the published port.

This is the core model: **you write what you want, MC2 makes it true and keeps
it true.** See [Desired state & reconciliation](/documentation/concepts/desired-state).
