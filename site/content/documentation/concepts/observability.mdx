MC2 tells you how it's doing in four ways: a health endpoint for supervisors,
a status summary for people, logs, and optional OpenTelemetry (OTLP) metrics
for dashboards. Per-sandbox CPU, memory, and network figures come from
microsandbox, not from MC2.

## Health and status

| Check | For | Answers |
| --- | --- | --- |
| `GET /health` | systemd, launchd, load balancers | Is the reconcile loop alive? `200`, or `503` with a reason once no pass has completed for 3 × the interval + 30 s. No token needed. |
| `mc2 status` / `GET /v1/status` | you | Version, instance counts, resource budgets and usage, public hostname. |
| `mc2 ps` | you | Every instance's phase, ports, and `NOTES` (disk warnings, failure reasons). |

## Logs

- **Server logs** go to stdout (default level `info`). Set the level with `RUST_LOG` (for example
  `RUST_LOG=mc2_server=debug`). They record applies, reconcile outcomes,
  restarts, and disk-condition changes.
- **Workload logs** come from each microVM: `mc2 logs <stack>/<service>/<ordinal>`
  (`--tail N` for the last lines, `--follow` to stream).

## OTLP metrics

`mc2 server` exports metrics over OTLP/gRPC when an endpoint is set. It uses
the first non-empty variable of:

1. `MC2_OTLP_ENDPOINT`
2. `OTEL_EXPORTER_OTLP_ENDPOINT`
3. `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`

There is no command-line flag. Set the variable before starting the server;
with none set, metrics are off. Metrics are exported every 15 s with
`service.name = mc2-server`.

```bash
export MC2_OTLP_ENDPOINT=http://127.0.0.1:4317
mc2 server
```

| Metric | Type | Meaning |
| --- | --- | --- |
| `mc2.server.applies` | counter | Stack applies |
| `mc2.server.schedule_binds` | counter | Instances placed on the server |
| `mc2.server.instances` | gauge | Instances, by attribute `phase` |
| `mc2.server.nodes_ready`, `mc2.server.nodes_total` | gauge | Always 1 in v1 (one embedded node) |
| `mc2.node.reconciles` | counter | Completed reconcile passes |
| `mc2.node.reconcile_errors` | counter | Failed reconcile passes |
| `mc2.instance.disk_used_mib`, `mc2.instance.disk_limit_mib` | gauge | Disk use and cap per instance; attributes `instance` and `target` (`root-disk` or `volume:<name>`) |

A reference collector configuration is in
`examples/90-advanced/observability/collector-config.yaml` in the
repository.

```text
 mc2 server ──OTLP/gRPC──┐
                         ├──► your OTel collector ──► Prometheus, Grafana…
 microsandbox metrics ───┘
```

## Per-sandbox metrics

MC2 doesn't re-export sandbox CPU, memory, or network usage. Those come from
microsandbox's own metrics component (`msb-metrics`); configure it per the
[microsandbox documentation](https://docs.microsandbox.dev) and send it to the
same collector to see both side by side.

## Key behaviors

- **Metrics are opt-in** and configured by environment only; restart the
  server to change the endpoint.
- **`/health` is for supervisors.** It turns `503` when the loop stalls, and
  the process exits non-zero if a critical task dies — let your service
  manager restart it.
- **Two sources, one collector.** Join MC2 and sandbox metrics at the
  collector.
