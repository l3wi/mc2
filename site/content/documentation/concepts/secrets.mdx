---
title: Secrets
description: Encrypted at rest, and only ever sent to the hosts you allow — the guest never holds the real value.
---

MC2 has two ways to put a value into a guest's environment. They look alike
in YAML, and both show up as environment variables, but they protect the
value very differently:

- `environment:` — plain configuration. The guest sees the real value.
- `secrets:` — credentials. The guest sees a placeholder; the real value is
  added only to connections to hosts you allow.

## The analogy

`environment:` is a variable written inline in a Compose file: plaintext,
readable by anyone who can read the file. A secret is closer to a credential
held by an outbound proxy: the application uses a stand-in, and the proxy
swaps in the real value only when the request is going somewhere approved.

## `environment:` — plain configuration

```yaml
services:
  web:
    image: alpine:3.20
    environment:
      MODE: fast
```

- Stored unencrypted in the stack, set when the microVM is created.
- Visible to every process in the guest and to anyone who can read the stack
  file or the data dir.
- Names starting with `MSB_` are rejected (reserved by microsandbox).

**Use for:** non-sensitive settings — ports, flags, feature toggles.

## `secrets:` — host-gated credentials

```yaml
services:
  web:
    image: alpine:3.20
    secrets:
      - name: SMOKE_TOKEN          # the stored secret
        env: API_TOKEN             # the variable the guest sees
        allowHosts:
          - api.example.com        # where the real value may go
```

The stack only **references** a secret by name. You set its value once, on
the server:

```bash
mc2 secret set SMOKE_TOKEN          # reads the value from stdin
```

### How a secret travels

```text
 mc2 secret set ──► server encrypts ──► mc2.db (ciphertext only)
                                            │  each reconcile pass
                                            ▼
                        decrypted in the server, handed to microsandbox
                                            │
 guest: API_TOKEN=$MSB_API_TOKEN ◄──────────┤  the guest gets a placeholder
                                            │
 guest ──TLS──► api.example.com   ──► proxy swaps in the real value
 guest ──TLS──► anywhere else     ──► refused if it carries the placeholder
```

- MC2's store encrypts values with XChaCha20-Poly1305 using the server's
  `secrets.key`. `mc2 secret ls` and the REST API return names and metadata,
  never values.
- The guest's variable holds a placeholder (`$MSB_<env>`). The microVM's
  outbound proxy inspects TLS connections and substitutes the real value in
  **HTTP headers** (including Basic auth) of requests to an `allowHosts`
  host — not in URLs or request bodies. A request carrying the placeholder to
  any other host is blocked and logged.
- `allowHosts` must list at least one host; an empty list is refused rather
  than treated as "anywhere".

**Use for:** API keys and tokens that should never sit in the guest in
plaintext.

<Warning title="The runtime keeps its own plaintext copy">
MC2 hands each running microVM's secret values to microsandbox, which stores
them **unencrypted** in its sandbox config (`~/.microsandbox/db`, or under
`$MSB_HOME`) for as long as that microVM exists. Protect that directory like
`secrets.key`: same user, mode 0700, excluded from shared backups. Also note
that an allowed host can send the value back in its response — the proxy
doesn't redact responses.
</Warning>

## Changing and removing secrets

- **Rotate** by running `mc2 secret set NAME` with the new value. On the next
  reconcile pass MC2 sees the value changed and **recreates** every instance
  that uses it — no re-apply needed. Plan for the restart, and keep data in
  volumes.
- **A missing secret fails only its consumers.** If a service references a
  secret that isn't set, each of its instances is reported `Failed` (the
  message names the secret) and everything else keeps running. Set the value
  and the next pass starts them.
- **Deleting a secret doesn't revoke it.** `mc2 secret rm NAME` marks its
  consumers `Failed` but keeps their existing microVMs — which still hold the
  old value. To revoke, remove the reference from the stack (or
  `mc2 down` the stack) as well, then rotate the credential at its source.

## Protecting the key

Secrets can only be decrypted with the key they were encrypted under:
`<data-dir>/secrets.key` (or `--secrets-key-path`), mode 0600.

- **Back up `mc2.db` and `secrets.key` together.** One without the other
  can't restore your secrets.
- If the key is missing or wrong and the database holds secrets, the server
  **refuses to start** rather than run with unreadable secrets.
- If the key is truly lost, `mc2 server secrets purge --data-dir <dir> --yes`
  deletes the stored secrets so the server can start; then set them again.

## Server-wide, not per stack

| | Compose | MC2 |
| --- | --- | --- |
| Declared | top-level `secrets:` in the project | nowhere — referenced by name |
| Stored | files or env, per project | the server's encrypted store |
| Visible to | one project | every stack on the server |
| At rest | plaintext on disk | encrypted |
| In the guest | real value (file or env) | placeholder; real value on allowed TLS only |

## Name collisions

If `environment:` and a secret's `env` set the **same** variable, the
`environment:` value wins. The secret is dropped (never decrypted for that
service) and a warning is logged.

## Key behaviors

- **Encrypted in MC2's store, never listed** — but see the runtime's
  plaintext copy above.
- **The guest never holds the raw value.** It is added per connection, to
  allowed hosts only.
- **Fail closed.** No hosts listed means no injection.
- **Rotation recreates consumers** on the next pass.
