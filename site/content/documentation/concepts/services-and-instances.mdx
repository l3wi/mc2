A **service** is a named description of a workload in a stack. An
**instance** is one replica of that service — one detached microVM. MC2
schedules instances, runs them through a phase model, and keeps them alive
according to the service's restart policy.

## The analogy

Like a Compose service, but each replica is a separate hardware-isolated
microVM with its own kernel, and the service is a *desired state* that MC2
keeps converged rather than a one-shot run.

## Phases

Instances move through a simple phase model, visible in `mc2 ps`:

| Phase | Meaning |
| --- | --- |
| `Pending` | Scheduled but not yet running — a first start waiting on `depends_on`. |
| `Running` | Sandbox booted; service command running. |
| `Failed` | Could not start or stay healthy; a reason is shown. |

With a `restart` policy, a failed or stopped instance is removed and
recreated instead of being left `Failed`. Repeated restarts are spaced by a
backoff (`2s`, `5s`, `15s`, then `30s`), reset after `60s` of continuous
`Running` — including restarts the runtime performs on a crashed sandbox
itself.

## Service keys

- **`scale`** — replica count. `scale: 3` creates three instances. With
  published ports, each replica gets a distinct host port: a fixed
  `published: P` becomes the block `P, P+1, …, P+N-1` (ordinal 0 keeps `P`);
  target-only ports get distinct auto-allocated ports. Allocations are stable
  across re-applies.
- **`restart`** — `no` | `on-failure` | `always` | `unless-stopped`. Drives
  node restart/recreate on failure. Every restart attempt is spaced by the
  backoff schedule (`2s`, `5s`, `15s`, then `30s`), and the counter resets after
  `60s` of continuous `Running`, so a crash loop cannot restart on every
  reconcile pass.
- **`command`** — guest argv as a list or a shell-split string. Omitted
  defaults to `sleep infinity` so a shell-less image stays alive.
- **`cpus` / `mem_limit`** — whole vCPUs (`1`–`255`; fractions are rejected)
  and guest memory (`512m`, `1g`, `1.5g`, or bytes).
- **`depends_on`** — startup ordering; see below.
- **`healthcheck`** — exec health probe that gates health.

## Addressing instances

Everywhere a command wants an instance, you can pass a UUID **or** the
human-readable `<stack>/<service>/<ordinal>` form:

```bash
mc2 exec shop/web/0 /bin/sh -c 'echo hi'
mc2 logs shop/web/2 --tail 20
```

## Health-gated startup

`depends_on` lets a service wait until a dependency is *healthy*, not just
started:

```yaml
services:
  db:
    image: postgres:16
    expose: [5432]
    healthcheck:
      test: ["pg_isready", "-q", "-U", "postgres"]
      interval: 5s
  web:
    image: alpine
    depends_on:
      db:
        condition: service_healthy
```

- List form (`depends_on: [db]`) means `condition: service_started`.
- `service_healthy` requires the dependency to declare a non-disabled
  healthcheck.
- References must be to services in the same stack; cycles are rejected at
  parse time.
- While waiting, the dependent reports `Pending` with a message like
  `depends_on: waiting for db (service_healthy)`.
- A dependency counts as live when **any** of its replicas is running
  (healthy, for `service_healthy`) — one `Failed` replica does not hide a
  healthy one.

## Key behaviors

- **Ordering at startup only.** The gate holds back a dependent's *first*
  start (and a recreate for a changed config). Once it is `Running`, a
  dependency going unhealthy does not tear it down, re-gate it or drop it from
  routing (Compose semantics).
- **`restart` is the resilience knob.** Without it, failures surface as
  `Failed`; with it, MC2 re-creates the sandbox, spacing repeated restarts by
  the backoff schedule.
- **Health drives convergence.** A passing probe sets an instance healthy,
  which unlocks `service_healthy` dependents.
