title: Storage

A **volume** is a named directory on the node that survives sandbox
recreation, restarts, and stack removal. It is the way state outlives a
microVM — everything inside the sandbox's own filesystem is ephemeral.

## The analogy

Like a Compose named volume, but backed by a directory on the MC2 node
rather than by the Docker daemon. Mount it where the service writes state;
that state persists across `restart`-driven recreates and across `mc2 down`
until you explicitly delete it.

## Declaring and mounting

Volumes are declared at the top level and referenced by services:

```yaml
volumes:
  data:
    kind: dir
    size: 10GiB        # optional; default 10 GiB

services:
  keep:
    image: alpine:3.20
    volumes:
      - name: data
        target: /data
```

- The top-level declaration is required — services cannot invent volumes.
- `kind: dir` is the only kind in v1. Disk images and snapshots are not yet
  supported.
- `size` is the volume's quota (compose byte sizes: `10GiB`, `512m`, or
  bytes), default **10 GiB**. Raise it with `mc2 up`: the VM restarts and the
  data is kept. MC2 refuses a size below what the directory already holds.
- Volume names must match `[a-z0-9][a-z0-9._-]*`, must not contain `--` or end
  with `-`, and are at most 63 characters.
- Mount targets must be absolute and unique per service.

## How names resolve

At sandbox create time, each mount resolves to the directory
`mc2-<stack>--<volume>` under the server's volume root
(`mc2 server --volume-dir`, default `~/.mc2/volumes`), and is mounted into the
VM as a bind mount with an explicit write quota of `size − current usage`.
Because the stack name namespaces the volume — and neither a stack nor a volume
name may contain `--` — two stacks can each mount a `data` volume without
colliding.

## Lifecycle

| Event | Volume survives? |
| --- | --- |
| Sandbox crash + `restart` recreate | Yes |
| `mc2 up` after changing `size` | Yes (VM restarts, data kept) |
| `mc2 down <stack>` | Yes (retained) |
| `mc2 down <stack> --volumes` | No (deleted) |

`mc2 volume ls` lists the volumes currently retained on the node (stack,
volume name, declared size, used size, path) — useful for verifying what a
destructive `down --volumes` would remove.

## Running out of space

A guest that fills a volume or its root disk sees the kernel's
`No space left on device`. MC2 detects both conditions and tells you where:
`mc2 ps` shows a `NOTES` entry (`volume data full`, `root disk 93%`), and
`mc2 exec`, `mc2 ssh open`, `mc2 logs` and `mc2 up` print the exact YAML change
to make. See
[troubleshooting](/documentation/operations/troubleshooting).

## Key behaviors

- **Ephemeral by default.** Writes to the sandbox rootfs vanish with the
  microVM; a volume is the explicit choice to persist. The root disk is sized
  per service (`storage_opt.size`, default 4 GiB) and is *recreated* — not
  grown in place — when you change it.
- **Every volume is capped.** The quota is passed on every VM start, so a
  runaway writer cannot fill the node's disk.
- **Single-consumer in v1.** Treat a volume as belonging to one service at a
  time; design caches/grids accordingly (e.g. one scale-1 cache service).
  Replicas that share one volume each receive the remaining budget at start, so
  concurrent writers can overshoot the declared size by up to
  (replicas − 1) × remaining.
- **`--volumes` is destructive.** It deletes the stack's volume directories.
